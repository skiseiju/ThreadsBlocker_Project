## 1. 先看這裡：清理名單的收集階段已修復，但**整體尚未 fixed**

**收集階段修好了**：實機在約 140 人的按讚貼文上，從長期只抓到 1 人變成**成功收集 37 人並提交**（`selectedCount: 37`、`committed: true`、`stopReason: "end"`）。

**但不得標記為 fixed**：beta74 實機回報仍會**偶發**出現「有勾選、也有收集到名單，但訊息說收集到 0 人」。詳見第 4 節 A2。收集能動 ≠ 整條流程正確。

使用者說明其餘未出現的帳號應是先前已被他封鎖（Threads 不顯示已封鎖帳號）。此說法與證據相容但**無法由診斷直接驗證**：可確認的是捲動確實到底（`scrollTop 1395 + clientHeight 1222 = scrollHeight 2617`），且連續 5 輪無新增。

### 根因是三個必須同時成立的缺陷

1. **容器選錯**：`Core.getTopContext()` 取 DOM 最後一個 `[role="dialog"]`。貼文預覽卡巢狀在清單 dialog 內、DOM 順序上必定在後，因此永遠選到只含作者一人的預覽卡。
   → 改用 `DialogCollector.pickBestAccountDialog()`（以精確帳號連結數挑選），收集器與勾選框注入共用同一份邏輯。

2. **scroll root 一次定生死**：候選條件要求元素「已經溢出」，但切到 Likes 當下只有 2 列、不可能溢出，於是回退成不可捲的外殼，之後每次 `scrollBy` 都是 no-op。
   → 改為迴圈內持續重解析，直到取得真正可捲的容器。

3. **捲動步長過大**：`Math.max(900, ...)` 的下限在任何小於 720px 的清單容器上，都會跳過整片未被採集的列（收集器只採當前可見列）。
   → 改為可視窗高的 0.8 倍並保留重疊。

**三者是連鎖關係**：容器選錯時，後兩者永遠沒有機會觸發。這是為什麼前兩次只修其中一項時，實機 log 與修改前一模一樣。

## 2. 已完成並實機驗證：停止鍵可見性（beta74 + beta76）

**狀態：✅ 使用者實機驗收通過（2026-07-22）。**

三個情境都正確：沒有 worker 執行時不出現、執行中出現、停止後消失不卡住。

**使用者回報**：「在未執行封鎖或檢舉 worker 時，底下會出現『停止執行』，這個應該是要在執行時再出現。」

**根因**：`src/core.js` 的 `resolveStopVisibility()` 把「佇列裡有待處理項目」（`activeQueue`）當成「正在執行」，使得佇列非空時按鈕就顯示——但當下沒有東西可停止。

**修法**：移除 `activeQueue` 對可見性的影響。新語義：
1. `activeSession`（`sessionActive` / `threeNoActive` / `state === 'running'` / `'stopping'`）為真 → 顯示
2. 否則 `terminal`（`idle`/`completed`/`stopped`/`failed`/`error`）為真 → 隱藏（**釋放 latch**）
3. 否則回傳 `!!input.stopLatch`（latch 在心跳過期、換頁等暫時性狀態中存活）

**必須保留 terminal 閘門**：`updateControllerUI`（約 3557 行）只在 `shouldShowStop` 為 false 時清除 latch。若 latch 一設起來就永遠回傳 true，latch 永遠不會被清除，停止鍵會卡在畫面上不消失——這會用另一條路徑重現原本的 bug。

**beta76 補上的關鍵一步（實機第一次驗收 FAIL 才發現）**：`terminal` 只認 `idle/completed/stopped/failed/error`。當 `bgStatus.state` 是**空字串或未知值**時 `terminal` 為 false，於是流程走到 latch——而 `Core._stopVisibilityLatch` 是從 localStorage 讀取（約 494 行 `readStopLatch()`），**會跨頁面重載與跨 session 殘留**，導致按鈕永遠顯示且清不掉。修正為 `if (terminal || !state) return false;`。

**最終閘門順序（不要打亂）**：
1. `activeSession` → true
2. `terminal || !state` → false（釋放 latch）
3. `input.stopLatch` → true（僅作為未知狀態值的防禦）
4. → false

由 `tests/beta74-stop-visibility-idle.test.mjs` 的 8 個案例保護，含兩個 regression 守門員：terminal + latch → false、空狀態 + latch → false。

**教訓**：beta75 那輪測試 163 全綠卻實機第一次就 FAIL，因為當時的規格（由主對話撰寫）把「狀態未知」誤判成「latch 該存活」，測試忠實地把錯誤行為固化。**測試只能守住你寫下的規格，守不住你想錯的地方。**

**驗收方式**：執行封鎖或檢舉時停止鍵應出現；只是佇列有待處理項目但 worker 沒跑時不應出現；停止後應消失不卡住。

## 4. 已知未解

### A. 貼文預覽卡上作者勾選框位置偏移（已決定擱置）

**使用者裁決（2026-07-21）**：「下一次再沒修好就算了，他不影響清理名單功能。」

**重要**：那個框是**發文者本人的勾選框，是有用的功能，要保留**。目標是移到帳號名稱旁，**不是刪除它**。beta71/72 曾花兩個版本試圖排除它，方向錯誤。

**根因（beta74 診斷實機數字證實，診斷已移除）**：
`injectDialogCheckboxes()` 推導列容器時，分支 1（有 followBtn 時沿父元素往上爬）會一路爬到巨大祖先。

| 對象 | 命中分支 | 容器高 | 連結高 |
|---|---|---|---|
| 正常使用者列（20+ 筆） | 1 | **42** | 21 |
| 作者頭像／名稱連結 | 1 | **2382** | 21-22 |

**未驗證的修法**：分支 1 加高度守衛，容器高 > `max(200, 連結高 * 8)` 就拒絕，讓流程落到 `a.parentElement` 回退。此修法曾實作但**從未實機驗證**，已隨還原一併移除。

**重查提醒**：診斷程式碼已不在 code 裡，要重寫。上次的寫法每個連結記一筆，導致 200 筆環狀緩衝中有 136 筆是 blocking/layout，把其他 feature 的紀錄全擠掉——**重寫時務必加取樣或筆數上限**。

### A2. 清理名單**未完全修復**：偶發回報「收集到 0 人」（beta74 實機回報）

**使用者回報（2026-07-22，beta74 實機）**：清理名單雖已能收集，但**偶發**出現「有勾選、也確實有收集到名單，但跳出的訊息說收集到 0 人」。

**因此不得把清理名單標記為 fixed。** 收集階段能動（37 人）只證明收集本身可行，不證明結果回報正確。

**早期就有證據被放過**：beta63 的 log 已出現 `selectedCount: 1`、`committed: true` 但 UI 顯示 0 人。當時被標成「獨立的顯示問題」延後，未回頭處理。

**尚未取得的證據（下次偶發時務必補齊）**：
1. **那則訊息的完整文字**——程式碼有三條路徑會產生「0 人」，文字不同、根因不同、修法不同：
   - `清理名單未完成：已開啟按讚名單，但沒有找到可勾選的帳號（看到 X 個帳號列，可勾選 Y 個）` → 收集被判定失敗，**會呼叫 `rollbackStagedCollection()`**
   - `已加入「0 選取」，請至清單「開始封鎖」` → 收集成功但加入時算出 0
   - `已將整串名單 0 人加入檢舉清單` → 檢舉清單路徑
2. **發生當下的診斷**：`stage: "commit"` / `"stop"` 的 `selectedCount`、`pendingCount`、`stopReason`，以及是否出現 `stage: "rollback"`
3. **勾選框當下是還勾著、還是被取消**

**已知的矛盾點（可能就是線索）**：若走回滾路徑，`rollbackStagedCollection()` 會還原勾選狀態，框應該被取消勾選。但使用者回報「框還勾著卻報 0 人」——代表**要嘛沒走回滾路徑，要嘛回滾沒真的生效**。這兩種情況指向不同的 bug。

**相關程式碼位置**：`handleCleanList` 的提交閘門（`shouldCommitDialogCollection`）與三處 toast；`collectFullDialogUsers` 迴圈結束後還會再呼叫一次 `collectRendered()`，若當下 dialog 已被拆除（曾觀察到 `clientHeight` 由 1224 掉到 0），該次重掃會把連結判為不可見。

## 6. 這個 repo 的測試品質問題（重要）

**大量既有測試在 grep 原始碼文字，而非驗證行為。** 例如 `tests/beta54-ui-route.test.mjs` 的 23 條斷言全部是 `assert.match(coreSource, /正規表示式/)`；`tests/beta50-status-priority.test.mjs` 甚至把原始碼切一段丟進 `Function()` 執行。

後果：

- **擋不住真 bug**：只要字面上有那幾個字就綠燈，邏輯寫錯照樣過。停止鍵這個 bug 能活這麼久，正是因為 beta50/52/54 三個檔案造成「有覆蓋」的錯覺
- **擋得住正當重構**：改個變數名就紅，跟對錯無關。本輪移除 `activeQueue` 就弄紅三個檔案

**因此：「測試 149/150 全過」不能當成行為正確的證據。** 新增測試一律要 `import` 產品模組驗行為，禁止在測試檔內重寫產品邏輯。

## 8. 除錯紀律（本輪最大教訓）

**涉及 DOM 結構的判斷，先出純診斷版取證，再動手修。沒有例外。**

本輪同一個 session 兩種做法、兩種結果：

- **清理名單**：照規矩先出 beta66 純診斷版 → 一輪定案 → beta68 一次修好
- **作者勾選框**：想省那一輪，連續假設 DOM 結構 → beta71/72/73 三次方向錯誤 → 最後仍得出 beta74 診斷版才找到根因，而那時已合理停損

**另一個陷阱**：fixture 會意外讓 bug 隱形。beta64 的測試把 dialog 寫成 `overflow:auto`，使「回退成 ctx」在測試裡剛好無害，於是 140/140 綠燈卻 1/140 實機失敗。寫 fixture 要加守衛斷言，一旦偏離實機形狀就直接失敗。

**還有**：不要預測「A 修好了 B 應該也會跟著好」。本輪預測「容器修對後勾選框會自動歸位」，錯了。
