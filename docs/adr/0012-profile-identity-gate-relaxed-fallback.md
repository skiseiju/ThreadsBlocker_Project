# ADR 0012：個人頁身分閘門改為「放寬」而非移除

- 日期：2026-07-29
- 狀態：已採納並實作（2.8.1-beta14，使用者實機驗證通過）
- 相關：BUGLIST #15、#11、`docs/BLOCKING_ARCHITECTURE.md`、`src/more-locator.js`

## 背景

2.8.0 起多數使用者回報無法封鎖，2.7.1 沒有此問題。

2.7.1 的 `Worker.findMoreButton` 對整份 `document` 做寬鬆搜尋加評分，幾乎不會空手而回；代價是它可能挑錯按鈕。2.8.0 為了避免點到錯的人，改成必須先通過 `Core.findProfileRoot`：

- `findProfileHeaderUsernameElement`：元素文字**一字不差**等於目標帳號，且落在相對 root 0–280px 的位置帶
- `findProfileActionAnchor`：頭部要有 Instagram 徽章／鈴鐺／更多按鈕

兩者 AND，過不了就回 `null`，上層直接記 `menu_not_found`，**沒有任何退路**。

這道閘門的失敗模式是全有全無：任一條件在真實版面對不上，就是整批 100% 失敗，而不是偶爾漏一兩筆。這與「多數使用者全面無法封鎖」的災情形狀吻合。BUGLIST #11 已在 beta10 修掉幾何那一半（小視窗把動作列擠出位置帶），名稱比對那一半直到 beta13 仍是一票否決。

## 決策：放寬身分證明，不移除

- **選項 A（採用）**：保留嚴格判定為主路徑；失敗時，在「網址確實停在本人個人頁」的前提下，改用寬鬆的名稱佐證再試一次。
- **選項 B**：失敗時退回 2.7.1 的整頁寬鬆搜尋。
- **選項 C**：維持現狀，只出診斷版蒐證後再決定。

選 A。

否決 B 的理由是不可逆的使用者代價。Threads 是 SPA，換頁時網址先更新、前一頁的 DOM 還留在畫面上一段時間。整頁搜尋在那個空窗期會抓到上一頁某個人的按鈕並照樣點下去，使用者看到「成功」，實際封鎖了不相干的帳號，而且要自己逐一解除。這正是 2.8.0 加上這道閘門的原因，不是潔癖。B 等於把已知的正確性問題換成容錯，方向錯了。

否決 C 的理由是時間成本與災情規模不成比例。災情是全面性的，等一輪診斷回來要多花數天；A 的守門測試已能證明認錯人的風險沒有放大，可以直接落地。

選 A 的具體內容：

1. `profileRouteMatches(username)`：比對 `location.pathname` 的 handle 是否等於目標帳號。這是放寬路徑的准入條件，用來擋 SPA 空窗期。
2. `findProfileUsernameEvidence(root, username)`：不看位置帶、允許 `@` 前綴，但仍排除 `[role="dialog"]` 與 `article` 內的文字。名稱只出現在貼文裡不算佐證。
3. 網址與 DOM 兩半都要成立才回 root。單靠網址不夠，因為網址會先於 DOM 更新。

## 決策二：放寬路徑必須留下痕跡

新增 `Core._lastProfileRootMode`（`strict` / `relaxed` / `none`）與 `relaxedRoot` 診斷欄位（布林，已加入 `_safeFields` 白名單）。`root_resolve` 的成功與失敗都會帶上。

理由：放寬是在沒有實機診斷的情況下做的判斷。如果不記錄「這一筆是靠放寬救回來的」，下次災情就無法分辨問題是回到嚴格那一半、還是根本在別處。BUGLIST #11 繞四個版本的教訓就是沒有證據先動手；這次至少要讓下一輪有證據可用。

## 後果

- 嚴格判定命中時行為完全不變，沒有效能或正確性代價。
- 放寬路徑的認錯人風險由網址閘門與「排除貼文內文字」兩條共同壓住，測試 `tests/beta14-profile-root-relaxed.test.mjs` 有兩項專門守這件事。
- 名稱比對本身仍可能有未知的失敗模式（例如頁面渲染的 handle 與儲存值不一致）。放寬只降低發生機率，沒有消除。`relaxedRoot` 的實機分佈是判斷要不要再往下走的依據。
- 檢舉流程（`report-flow.js:511`、`831`）**也呼叫** `Core.findProfileRoot`，因此一併繼承放寬路徑，這不是可選的。判斷是可接受：放寬仍要求網址與 DOM 兩半都證明身分，而檢舉在點擊之後另有 `MoreLocator.routeMatches` 的導航守衛（BUGLIST #13 的 `navigation_mismatch` 即由它產生）。若日後要讓檢舉維持較嚴格的門檻，必須顯式傳入模式參數，不能靠「檢舉沒用到」的假設——本 ADR 初稿就寫錯過這一句。
- 連帶影響：BUGLIST #10／#13 的檢舉失敗若有一部分源自 `findProfileRoot` 回 `null`，本次放寬會一併降低發生率。這是附帶效果，不是那兩項的修正，兩項仍維持 Open。
