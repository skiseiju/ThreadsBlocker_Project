# ADR 0007: 帳號 ID 雜湊上傳 + 存量資料再處理（不遷移）

- 日期: 2026-07-06
- 狀態: 已採納
- 相關: [SDD_Topic_Amplification.md](../SDD_Topic_Amplification.md) §5

## 背景

程式碼查核（src/reporter.js:72-87、src/storage.js:1060）顯示被封帳號的 username 以原文出現在平台上傳 payload 中，與「不上傳被封者 ID」的原始設計認知不符。Threads 帳號名可間接識別自然人，屬個資法上的個人資料；蒐集依據為 §19①7「一般可得之來源」，但原文儲存放大了風險面。跨觀測者交叉驗證（89,418 帳號被多人封鎖）是產品最有力的數字，計算上只需「同帳號映射到同值」，不需要原文。

## 選項

1. **維持原文上傳**——法律上可辯護但風險面最大，且非必要
2. **雜湊上傳 + 存量資料全面雜湊遷移**——合規最徹底，但破壞性改寫 D1 原始資料，未來若需人工複核或改演算法即無路可退
3. **雜湊上傳 + 存量 raw 保留、公開呈現走再處理層**——新資料上傳前 SHA-256 加鹽；既有 raw data 不動，另建 derived tables，處理時對 raw username 施同鹽雜湊做交叉計數，公開 API 只讀 derived

## 決定

採選項 3（海哥定案：「不是遷移，是再處理」）。要點：

- 擴充功能 schema 升版 `platform_upload.v3`：accountId 上傳前 SHA-256 + 固定鹽
- **前台永不呈現任何帳號識別**——原文不行，雜湊值也不呈現
- raw 層與 derived 層權限分離；raw 表以 checksum 驗證零改動
- snippet/sourceText（貼文原文 160 字）僅供分群運算，永不進公開 API，保存期限納入隱私聲明

## 後果

- 正面：新資料鏈路去識別化；原始證據保全（未來演算法改版可全量重算）；公開面只有聚合數字，個資法風險面最小化
- 負面：raw 層存續期間仍持有原文個資，須以存取權限與保存期限管理；同鹽雜湊若鹽外洩可被字典攻擊反查（鹽存 Worker secret，不進 repo）
- 衍生工作：platform-sync-v2 同意文案隨 schema v3 改版；site/privacy/ 隱私聲明補蒐集範圍與保存期限
