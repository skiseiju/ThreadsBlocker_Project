# ADR 0013：問題回報預設附帶輕量診斷

- 日期：2026-07-29
- 狀態：已採納並實作（2.8.1，待使用者確認後送審）
- 相關：ADR 0010（consent v4）、ADR 0011（試算表同步）、ADR 0012（身分閘門放寬）、`docs/CWS_PRIVACY_PRACTICES.md`、`site/privacy/index.html`

## 背景

2.8.0 多數使用者回報無法封鎖。收到的每一封回報都只有一句文字描述加版本號，沒有任何可供定位的線索，根因是隔了兩週、靠人工比對 2.7.1 與 2.8.0 的程式碼才找出來的（見 ADR 0012）。

原因不是漏送，是設計上就關掉了：

```js
// 舊 RuntimeDiagnostics.enabled()
CONFIG.ENABLE_BETA_DIAGNOSTICS === true && /-beta\d+$/i.test(CONFIG.VERSION)
```

這一條同時控制三件事：ring buffer 要不要收集、回報視窗的診斷勾選框要不要顯示、以及手動 debug／export UI 要不要出現。正式版三件事一起關掉，因此使用者連「想附診斷」都沒有選項。

值得注意的是，ring buffer 的內容早就設計成隱私安全的：`RuntimeDiagnostics._safeFields` 是封閉白名單，只放有界整數、布林與預先定義的列舉代號，不含帳號名稱、選單文字、頁面網址或 log。真正敏感的是另一包完整附件（含 console log 與頁面資訊）。兩者被同一個開關綁在一起，是這次查不到根因的直接原因。

## 決策一：把一個閘門拆成三個

| 閘門 | 條件 | 控制什麼 |
|---|---|---|
| `RuntimeDiagnostics.enabled()` | `CONFIG.ENABLE_RUNTIME_DIAGNOSTICS`（預設 true，所有版本） | ring buffer 收集 |
| 逐次 checkbox 同意 | 使用者當次勾選 | 完整診斷附件 |
| `RuntimeDiagnostics.betaDebugUI()` | `ENABLE_BETA_DIAGNOSTICS` 且版本為 `-betaN` | 手動複製／清除診斷、三無 verbose log |

第三個維持 beta 綁定，因為 `AGENTS.md` 要求正式版移除 beta-only 手動 debug/export UI。前兩個與版本無關。

`ENABLE_RUNTIME_DIAGNOSTICS` 保留為緊急關閉用的總開關。

## 決策二：輕量層預設送，不設勾選框

- **選項 A（採用）**：輕量層一律附帶，在回報視窗以蒐集時點揭露說明內容，不設勾選。
- **選項 B**：輕量層也要勾選同意。
- **選項 C**：勾選框預設打勾。

選 A。

否決 B 的理由是它不解決問題。既有的完整附件勾選框就是 B 的形態，實際結果是使用者不勾，維護者拿不到線索，功能故障長期修不好。把同一個機制再做一次，預期結果一樣。

否決 C 的理由是預設打勾的同意在商店審查上站不住腳，而且它宣稱取得了實際上沒有取得的同意，比誠實揭露「一律附帶」更糟。

選 A 的正當性建立在三件事上，缺一則此決策不成立：

1. 內容由封閉白名單產生，不含任何可辨識個人的資料，也不含使用者正在瀏覽的內容。
2. 只在使用者主動送出問題回報時才傳送，不是背景上傳。
3. 在送出前的畫面上直接揭露，不是只寫在隱私政策裡。

## 決策三：誠實揭露關聯性

輕量層與既有的持續性隨機回報 ID 一起送出，因此同一個安裝來源的多次失敗可以被串起來。隱私頁與商店申報都要明寫這一點，不能只說「不含個資」就帶過。

這延續 ADR 0010 的立場：寧可揭露得比實際做的多，不可反過來。

## 決策四：備援端點不保存診斷

`gas_bug_reporter/bug_report_server.gs` 掛在 `BUG_REPORT_FALLBACK_URLS`，只有主要 Worker 失效時才會被呼叫，而它原本把整包 `metadata` 直接寫進試算表欄位。輕量層一開，診斷就會流進一張沒有為它設計過、也沒寫進隱私政策的試算表。

改為只記錄「本次有沒有附件」。備援存在的目的是不要漏掉使用者的求救訊息，診斷不是必要的。

## 決策五：補上讀得回來的路徑

`handleAdminList` 刻意不撈 `metadata`，且沒有任何其他 endpoint 讀得到它。也就是說在本 ADR 之前，即使診斷送達，維護者也拿不出來——資料進得去、出不來。

新增 `GET /api/v1/admin/bugs/:id`，唯讀，走既有的 `reports:read` scope，不新增任何寫入路徑。

## 後果

- 正式版使用者的問題回報從「一句話」變成「一句話 + 可定位的步驟代號」。這是本 ADR 的全部目的。
- 商店隱私申報的資料類別**沒有新增**，`User activity` 本來就已申報；變的是送出條件。CWS 與 AMO 都要以新口徑重新送審。
- 送出的資料變多，代表出錯的代價也變高。白名單是唯一的防線，任何往 `_safeFields` 加欄位的修改都必須確認新欄位不含文字內容。
- 三個閘門日後有被合併回去的誘因（看起來重複）。`tests/beta15-lightweight-diagnostics.test.mjs` 第一項測試就是為了擋這件事。
- 每日試算表同步（ADR 0011）不受影響：它的匯出欄位清單不含 `metadata`，診斷只會留在 D1。
